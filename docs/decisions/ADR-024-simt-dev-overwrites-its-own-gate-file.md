# ADR-024 — simt-dev overwrites its own gate file, and no repository else's

Status: accepted · 2026-10-06
**Affects:** `src/ci/workflow.mjs`, `src/commands/ci.mjs`, `src/commands/init.mjs`,
`src/commands/index.mjs`, `src/commands/help.mjs`, `src/projection/project.mjs`,
`.github/workflows/simt-dev-check.yml`, `test/ci.test.mjs`. Supersedes ruling 2 of
[ADR-023](ADR-023-the-gate-ships-as-a-file-the-repo-owns.md), and narrows its rulings 3 and
4 to every repository except this one. ADR-023's rulings 1, 5 and 6 stand.

## Context

ADR-023 copied the gate into `.github/workflows/` and wrote it once. For an adopting
repository that is the right call, and the cost was written down rather than discovered
later: a template improvement does not reach a repo that already has the file.

This repository is not an adopting repository. It is the tool. And a tool whose own gate is
a frozen copy of its own gate is a tool with two gates, one of which it does not maintain.
The file `.github/workflows/simt-dev-check.yml` in this repository was written by the
template, and every future change to the template would leave it behind — silently, because
ADR-023 ruling 4 says `check` never inspects a workflow's contents, so nothing would report
the gap. A gate that cannot report its own staleness is the failure mode ADR-017, ADR-018
and ADR-019 were each written about.

There is a second reason the exception is narrow rather than general. **A rule with one
exception is a rule with an exception; a rule with a flag is a rule with two behaviours
depending on who asked.** The write-once ruling is what protects a repo's deployment job
from being overwritten. "Unless the tool feels like it" is not a boundary anyone can check.
The only boundary that needs no judgement is a path, and this repository is one path.

## Rulings

1. **This repository's gate file is generated, refreshed, and generated bytes only.** It
   lives at `PACKAGE_ROOT`, recognised by `resolve(root) === PACKAGE_ROOT` — not by a
   flag, an env var, or a name in a config file, because all three can be set by a consumer
   who would then have found the one path that overwrites their CI. `resolve`, not
   `realpath`: a symlinked checkout that fails to match leaves it a consumer, which is the
   direction a mistake is survivable in.

2. **`simt-dev ci` is the only writer of that copy, and it is a dry run without `--yes`.**
   `init` cannot be the writer, and this is not a design preference. `init` on this
   repository would pin this repository's SHA into its own `AGENTS.md`, which is precisely
   what the "Why this repository is not self-adopted" section of `AGENTS.md` exists to
   prevent. A refresh reachable only through `init` is an exception that can never fire, and
   an exception that cannot fire is worse than no exception: it reads in the code as though
   the copy were maintained.

3. **`simt-dev ci` outside this repository is a refusal, not an error.** It prints who owns
   the file and the command that owns it (`simt-dev init --yes`), writes nothing, and exits
   zero. A refusal is a report. Making it a failure would mean a CI job that runs `ci`
   before it runs `check` breaks for every adopting repo, for a condition that is correct.

4. **The header of each copy says which world it is in.** The consumer copy says it is
   written once and never rewritten. The own copy says it is refreshed, that a diff means
   the **gate** changed rather than that somebody hand-edited their CI, and that the way to
   change it is `src/ci/workflow.mjs` in the same commit followed by `simt-dev ci --yes`.
   Both sentences are tested against the rendered bytes. The alternative is a reader of this
   repository's diff seeing their CI change and having to guess who did it.

5. **This repository's copy is compared; every other repository's is not.** `planWorkflow`
   computes `current` only when the root is this repository's, and `check` raises a
   `drift` finding with the remedy `simt-dev ci --yes` only then. ADR-023 ruling 4 stands
   unchanged for everyone else: their file, their content, never opened.

6. **This repository's copy runs the gate this repository can actually pass.** The consumer
   copy runs `simt-dev check`, which fails here by design — `check` reports
   `UNMANAGED AGENTS.md` in a repository that has deliberately not adopted itself, so a copy
   of the consumer workflow committed here would be red on its first run and every run after.
   The own copy runs what `.githooks/pre-push` already runs — `npm test` and
   `graph lint` — plus `simt-dev ci` itself, so the file is its own staleness check. A test
   asserts both commands are in the hook and in `package.json`, because a gate that names a
   command this repository does not have is ADR-019 again.

7. **Both copies render from one skeleton.** Triggers, permissions, concurrency, runner and
   timeout are written once in `skeleton(name, steps)`; the two renderings differ in the
   header text, the job name and the steps. Two independently written YAML files are two
   opinions about when a pull request is gated, and the copy that is wrong is the copy nobody
   diffs.

## Consequences

- `simt-dev ci` is a new command with one job. It is also the first command in this tool
  that only makes sense in the tool's own repository, and that is deliberate: it is the
  only honest way to ship a self-maintained generated file without giving the write-once
  ruling a flag.
- `test/ci.test.mjs` now has one test that writes into this repository: it mutates the
  committed workflow, asserts `check` reports the drift, runs `ci --yes`, asserts the bytes
  are restored, and restores in a `finally`. No fixture can produce this case, because the
  condition *is* this repository's path. The test is therefore the only one that can fail
  for an environmental reason, which is why it restores rather than only asserting.
- The own copy is checked with the leak rules but not with the path rules. Naming
  `src/ci/workflow.mjs` in this repository's own workflow is correct — it is the one place
  that path resolves — so asserting against it would be asserting that this repository's
  CI cannot mention its own source.
- If this repository is ever vendored or installed as a package, `PACKAGE_ROOT` becomes a
  directory under `node_modules` with no `.git` and no workflows, and the copy simply stops
  existing there. Nothing needs to detect that case.

## Rejected

- **A `--managed` flag, or `init --refresh-ci`.** Rejected under ruling 1: it makes the
  difference between "never overwrites your CI" and "will overwrite your CI" a value the
  consumer sets. The ruling is worth more if there is no spelling for the wrong answer.
- **Let `upgrade` refresh the file in every repo.** Rejected: it is the merge-strategy
  problem ADR-023 already declined, and adding a repository to the exception list is
  strictly smaller than solving it for all of them.
- **One workflow file that detects which repo it is in at run time.** Rejected: a consumer's
  file would then contain this repository's path and its commands, which is ADR-023 ruling 1
  violated inside the very file ruling 1 was written for.
- **Give the own copy a managed region marker instead of full replacement.** Rejected: this
  repository has no hand edits to preserve, so a merge strategy would be machinery for a
  case that does not exist here and would leak into the consumer copy's design.
