# ADR-207 — the surface has one inventory, and one stability statement per name

Status: accepted · 2026-11-21 · filed as review 0005 PR29

## Context

Seven entry points described this tool, and each answered a different question:

- `src/commands/spec.mjs` named every dispatchable path, its flags and whether it writes.
- `--help` divided the paths into a core and an advanced page.
- `src/api.mjs` exported 25 functions through `package.json` `exports`.
- `src/mcp/tools.mjs` exposed a subset of commands as tools, plus one with no row.
- `package.json` also exposed `./src/*`, which publishes every internal module path.
- The shims and the CI template resolved a binary or a devDependency.
- The generated command and module pages restated the spec's rows.

A tier is where a command is listed, not a promise about it, so none of those was a
stability statement. `pack` carried `stability: 'experimental'` and nothing else did; the
bench corpus, the work/action/verification doors, distillation, federation and the
compatibility aliases had no classification at all. A reader could not tell a supported
adoption command from a research prototype, and PR30–PR32 (which retire, move and narrow
parts of the surface) had no recorded baseline to retire *from*.

## Ruling

1. **One inventory.** `src/surface.mjs` maps every dispatchable path to exactly one
   disposition, and the inventory is derived from the spec rather than restated. A group
   the table does not name makes `dispositionOf` throw; it does not default to stable. The
   same module lists the library exports and the package export map, and the page rendered
   from it (`docs/reference/surface.md`) is regenerated by `simt docs commands --yes` and
   compared byte for byte by `test/docs.test.mjs`.

2. **Four words, no synonyms.** `stable` (a compatibility promise: removal is a
   deprecation first), `optional` (shipped, supported when used, not the adoption path),
   `prototype` (reachable for a design partner, no compatibility promise), `experimental`
   (published, frozen, gains no feature until a real consumer adopts it). A fifth word for
   one group would be a second vocabulary to learn.

3. **The review's named surfaces are settled by name.** Bench, pack, distill, the
   work/action/verify prototypes, federation, workspace sharing and the aliases each appear
   in `NAMED_SURFACES`, and a test fails when one of them loses its disposition. Bench,
   distill, local models, plugin generation and federation are `optional`; packs stay
   `experimental` (ADR-130); work, action/adapter verification and knowledge exchange are
   `prototype`; workspace sharing and the aliases stay `stable`.

4. **The library surface is the runtime namespace.** `API_EXPORTS` is compared with
   `Object.keys(await import('simt-dev'))`, so a new `export` in `api.mjs` arrives without a
   stability statement only by failing the test.

5. **Deprecations are recorded with a replacement and a window.** `sync --check` (the
   spelling bare `sync` replaced) and the `./src/*` deep imports are listed in
   `DEPRECATIONS` and in the page. The wildcard is not removed here: the generated plugin
   runtime imports through it, and replacing it is PR32's action. Recording it now is what
   makes that removal scheduled rather than a surprise.

6. **Aliases are a supported spelling, not a second command.** Every alias in the spec is
   published with its target, adds no capability, never appears in help, and stays until
   the next major. Removing one is a deprecation like any other name.

## Consequences

- Adding a command group is now a two-part change: the spec row and its disposition. The
  second one is a decision about the promise, which is what the review asked for.
- `docs/reference/surface.md` is generated and must be regenerated (`simt docs commands
  --yes`) in any slice that adds a path, export or tool. It is checked like the other
  reference pages.
- The page lists 46 command groups, one row per path, 25 library exports, three package
  exports and two deprecations. It does not replace the command reference: the spec page
  carries flags, this one carries stability.
- PR30–PR32 now have a baseline to act on: pack is frozen and marked, bench/distill are
  optional rather than core, the work/action/verify doors are prototypes, and `./src/*` is
  a recorded deprecation.

## Alternatives

- **Put stability on every spec row.** 100+ literals to keep in step, and a group would
  still need a default for the rows nobody revisited. The group table plus explicit path
  overrides states the same facts once.
- **Use the help tier as the stability statement.** The tier is where a command is
  *listed*; `skills eval` is advanced and supported, `bench report` is core-adjacent and
  optional. They answer different questions, and conflating them hides both.
- **Remove `./src/*` in this slice.** The plugin runtime imports through it today; removal
  without a replacement path is the defect PR32 exists to avoid.
- **Keep the hand-written page.** The MCP reference was 15 of 32 tools before it was
  generated; a stability page hand-written once would be wrong at the next command.
